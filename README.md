## What this project does

*Lucknow Tea Growers' Estate* pays workers by the kilo and plans factory shifts from the expected leaf.
We predict **`kg_per_worker`** (kg plucked by one worker in one day, a regression problem, measured with **MAE**)
and wrap the model in a full MLOps pipeline: versioned data, tracked experiments, a model registry, a prediction API,
a container, CI, Kubernetes files, JSON logs, drift monitoring and a retrain.

## The data problems we found (all by code in `src/mp024/data_checks.py`)

| Problem | Present? | What we found | What cleaning does |
|---|---|---|---|
| `leaking_column` | yes | `kg_weighed_at_factory` - missing from the holdout file, rank correlation 0.98 with the target | dropped, never a feature |
| `unit_mixup` | yes | `rain_mm_week` for **River Side** is ~10x smaller (cm instead of mm); `factor = 0.1` (wrong = right x 0.1) | River Side rain divided by 0.1 |
| `sentinel_value` | yes | `worker_exp_yr = 9999` in 40 rows | set to missing, median-imputed inside the model pipeline |
| `duplicate_rows` | no | 0 extra copies (also none ignoring `record_id`) | - |
| `stuck_sensor` | no | longest run of identical readings in any column is 3 rows | - |
| `target_typos` | yes | 9 targets typed 10x too big (206 ... 367 kg; the rest stop at 53.7) | divided by 10 |
| `spelling_variants` | yes | `flush` written 18 ways, 3 real levels (`first`, `second`, `monsoon`) | mapped to the 3 levels |

## How to run

```bash
pip install -r requirements.txt          # Python 3.12
# data: the originals live in data/raw/ (or `dvc pull` if a DVC remote is configured)

./run_pipeline.sh                        # checks -> train v1 -> monitor + v2 + decision -> holdout -> findings.yaml
pytest -q                                # 26 tests

# the service
uvicorn app.main:app --port 8000         # needs PYTHONPATH=src:.   (the Docker image sets it)
curl localhost:8000/health
curl -X POST localhost:8000/predict -H 'content-type: application/json' \
  -d '{"worker_exp_yr":10,"rain_mm_week":120,"slope_deg":15,"temp_c":24,"bush_age_yr":40,"hours_worked":9,"flush":"first","section":"River Side"}'

# container + Kubernetes
docker build -t mp024-api:1.0 .
docker run -p 8000:8000 mp024-api:1.0
kubectl apply -f k8s/
```

## Client rules (enforced in the pydantic request schema -> HTTP 422)

* `hours_worked` above 15 is rejected (`Field(le=15)`).
* `rain_mm_week` below 0 is rejected (`Field(ge=0)`).
* The body must contain exactly the eight fields; extra fields (e.g. the leaking column) are rejected too.

## Design decisions

* **Cleaning is driven by the detected findings**, not hard-coded, so the code that answers `findings.yaml` is the code that cleans.
* **The leaking column is never a feature.** It would give a near-perfect score and fail in production, because it only exists after the event.
* **Model choice:** a ridge regression with pairwise interactions (e.g. section x hours) won cross-validation on train, and it also
  extrapolates linearly, which matters because `later.csv` has much longer working hours (up to ~13 h) than train (max 10 h).
  Tree models cannot predict beyond the largest value they saw.
* **v2 = the same recipe retrained** on train + first 70% of later; the promotion rule is code (`promotion_decision`) and tested.
* **Logging:** one JSON line per prediction on stdout, agronomic inputs only - no personal details of any worker.
